01 · Problem Statement

Requirements & Use Cases

A research datacenter fleet — A100/H100/H200 GPU nodes, Intel Xeon CPU nodes, and petabytes of ION SSD storage — already runs Kubernetes out of the box. The missing piece is a self-service layer: researchers should never file a ticket to get compute, and operators should never hand-carve namespaces or clusters by hand.

Functional requirements

IDRequirement
F1Discover — list datacenters, node pools, GPU SKUs, MIG availability, storage classes, and live free capacity.
F2Create — provision an isolated environment in a chosen DC, in namespace mode (default) or virtual-cluster mode, with a resource envelope (GPUs, CPU, RAM, storage).
F3View — list & inspect own environments: status, quota, live usage, endpoints, kubeconfig.
F4Upscale / downscale — grow or shrink the resource envelope; subject to quota & capacity checks; asynchronous with observable progress.
F5Delete — tear down an environment and reclaim every resource, with confirmation and grace period.
F6Access — hand back working credentials (kubeconfig) scoped strictly to the tenant's environment after successful creation.

Non-functional requirements

IDRequirement
N1Utilization first — bin-packing many tenants onto shared silicon is the raison d'être; hence the namespace-first preference.
N2Isolation — tenants must not see, starve, or attack each other (API, network, data, GPU memory).
N3Global scale — one management plane spanning multiple datacenters; a DC outage must not take the plane down, and vice versa.
N4Auditability & metering — every mutation attributed to a user; GPU-hours accounted per tenant for showback/chargeback.
N5Idempotency — creates/scales/deletes are retry-safe; long operations are asynchronous and observable.
N6Familiar UX — researchers keep plain kubectl after provisioning; the tool follows established CLI conventions.

Actors and their journeys

Three personas interact with the system. The researcher discovers hardware, requests an environment, receives a kubeconfig, and runs training or inference jobs. The platform operator registers datacenters, defines hardware pools and quota policies, and watches fleet utilization. The automation client (a CI pipeline or an ML workflow engine) uses the REST API to create ephemeral environments programmatically — which is exactly why the API must exist even in a CLI-first product.

Terminology used throughout

We call the provisioned unit an environment with a mode of either namespace (a policy-wrapped set of namespaces on a shared cluster) or vcluster (a virtual control plane whose pods still land on shared nodes). Kubernetes itself has no first-class “tenant” concept — the platform must construct one from namespaces, RBAC, quotas and policies [1].

02 · The Central Debate

The Tenancy Spectrum: Namespace vs Virtual Cluster vs Dedicated Cluster

Isolation in Kubernetes is not a binary of “hard” and “soft” but a spectrum [1]. Every step up the ladder buys isolation and autonomy at the cost of utilization, cost, and operational complexity. Choosing where ClusterOnDemand sits on this ladder — and whether it offers one rung or several — is the single most consequential design decision.

D1. The tenancy ladder. ClusterOnDemand exposes Tiers 1–2 as self-service modes and reserves Tier 3 for exceptional cases; fully dedicated clusters are deliberately out of self-service scope.

What each rung actually is

Namespace-based tenancy groups a tenant's workloads into one or more namespaces on a shared cluster, enforcing isolation with RBAC, ResourceQuota, LimitRange, and default-deny NetworkPolicy [1]. Plain namespaces alone are insufficient — quotas and policies attach to namespaces, not tenants, so a tenant with three projects triplicates every policy. Operators like Capsule fix this with a Tenant CRD that aggregates quota across a tenant's namespaces and lets tenant users self-create namespaces with plain kubectl [6], while the Hierarchical Namespace Controller propagates policies down namespace trees [4].

Virtual clusters (vCluster and the CAPI-nested VirtualCluster) give each tenant a real API server, controller-manager, and datastore running as pods inside a host-cluster namespace; a syncer copies pod specs down to the host, so workloads still schedule onto the shared node fleet [4] [5]. Tenants get cluster-admin, their own CRDs and operators, and even their own Kubernetes version — without new hardware.

Hosted control planes (Kamaji, HyperShift, Gardener) also run control planes as pods in a management cluster, but attach dedicated worker nodes that join remotely — the model hyperscalers use internally for EKS/GKE/AKS [7]. Dedicated clusters per tenant maximize isolation and are sometimes forced by regulation, but multiply control-plane hardware, upgrades, and monitoring stacks — the classic cluster-sprawl failure mode [3] [4].

D1

Debate: Should namespace mode really be the preferred default?

✓ The case for namespace-first
  • Utilization is the mission. Every tenant shares one scheduler and one node fleet, so idle GPU capacity from tenant A is instantly available to tenant B — no stranded capacity behind per-tenant fences. This is your stated goal, and the data agrees: naive sharing schemes leave GPUs at ~40% utilization and tenant-level pooling is the fix [5].
  • Seconds-fast onboarding — creating a namespace + policy bundle is a handful of API calls; no control plane to boot.
  • One observability & security stack — a single Prometheus/DCGM, one policy engine, one upgrade train [2].
  • Researchers are semi-trusted colleagues, the canonical “multiple teams” case where namespace tenancy is designed to work [1].
✗ The case against (and mitigations)
  • Shared control plane blast radius — an abusive client can flood the API server or CoreDNS. Mitigate: API Priority & Fairness, per-tenant rate limits [1].
  • CRDs and webhooks are cluster-scoped — tenants cannot bring their own operators (Kubeflow, Ray, custom CRD versions) without colliding [4]. Mitigate: platform-curated shared operators + Tier 2 escalation for the rest.
  • Kernel-level co-tenancy — containers share the node kernel; a breakout reaches neighbors. Mitigate: Pod Security Standards, seccomp, no-privileged admission policies, and MIG's silicon-level GPU partitioning [1] [5].
  • Noisy neighbors on network/IO — quotas don't cover bandwidth. Mitigate: CNI bandwidth annotations, storage QoS classes [1].
Verdict

Namespace mode as the default is the right call for a research fleet whose tenants are accountable, identifiable colleagues — but only if it ships as a hardened bundle (tenant CRD + RBAC + default-deny netpol + aggregated quota + admission policies), never as bare namespaces. Offer vCluster as a first-class second tier for the meaningful minority who need their own CRDs, operators, or API-server autonomy: it preserves the shared-node utilization story while removing the shared-control-plane objections [2] [5]. This tiered design converts the namespace-vs-vcluster argument from an either/or into a product feature (--mode flag).

03 · Resource Model

GPU, CPU & Storage Resource Model

The hardware catalogue — A100/H100/H200 GPUs, Xeon CPU pools, and ION SSD tiers — must be surfaced to researchers as schedulable, quota-able, meterable resources. GPUs dominate this design because they are the scarcest, most expensive, and least naturally shareable asset in the fleet.

How a GPU becomes multi-tenant

By default Kubernetes treats a GPU as an opaque integer: a pod requests nvidia.com/gpu: 1 and monopolizes the whole device, even if it uses 15% of it [8]. Three NVIDIA sharing mechanisms change that, and they differ profoundly in isolation guarantees:

D2. GPU sharing mechanisms. MPS (not shown) offers software concurrency for co-operative CUDA clients within one trust boundary, but a single fatal client fault can poison the whole GPU — unsuitable for cross-tenant sharing [8].

Node pools, flavors, and the capacity catalogue

Each datacenter cluster is carved into labeled node pools: pool=h100-sxm (NVLink-coupled training), pool=h200 (large-memory inference), pool=a100-mig (MIG-partitioned shared pool), pool=a100-ts (time-sliced dev pool), and pool=xeon-highmem (CPU/data-prep). ClusterOnDemand abstracts these into flavors — the unit researchers actually request:

flavor: gpu.h100.full      → 1 × H100 SXM 80GB, 24 vCPU, 192Gi RAM   # whole device
flavor: gpu.h100.mig-3g    → 3g.40gb MIG slice, 12 vCPU, 96Gi RAM     # hard-isolated slice
flavor: gpu.a100.mig-1g    → 1g.10gb MIG slice, 4 vCPU, 32Gi RAM      # smallest sellable GPU unit
flavor: gpu.dev.shared     → time-sliced GPU slot (no SLO)            # notebooks, tutorials
flavor: cpu.xeon.large     → 32 vCPU Xeon, 256Gi RAM                  # data prep, CPU jobs
storage: ion-nvme-fast | ion-nvme-std | object-archive                # StorageClasses w/ QoS tiers

Separating training, inference, and dev workload classes onto different pools is an operational best practice: long-running training saturates memory for days, while inference is bursty — co-locating them on the same shared device degrades both [5]. Storage follows the same pattern: StorageClass tiers with distinct QoS and reclaim policy Delete so PersistentVolumes are never reused across tenants [1].

Debate: Which scheduler arbitrates GPU contention?

The vanilla Kubernetes scheduler has no notion of gang scheduling, queueing, or GPU topology — a 64-GPU distributed job can deadlock half-scheduled while small pods fragment the fleet [9]. Four credible options exist:

Start with Kueue for tenant-level queueing and quota borrowing (it composes with the default scheduler and with Capsule-style tenants), plus bin-packing scoring (MostAllocated) on GPU pools so idle nodes fully drain [5]. Introduce KAI Scheduler selectively where gang scheduling and consolidation earn their complexity. Note that if H100/H200 hardware was purchased with bundled NVIDIA AI Enterprise, Run:ai entitlements may already exist and are worth checking before dismissing it [9].

04 · System Design

Global Management-Plane Architecture

ClusterOnDemand is a two-plane system: a Global Management Plane (the “hub”) that owns identity, inventory, quota, placement, and the public API — and a lightweight agent (the “spoke”) inside every datacenter's Kubernetes cluster that does the actual provisioning by reconciling declarative desired state.

D3. Two-plane architecture. Researchers converge on the hub API; after provisioning, their kubectl traffic goes directly to the tenant environment in the datacenter — the hub is never on the workload data path.

Hub components

The API Gateway terminates OIDC (institutional SSO — researchers already have identities), enforces per-principal rate limits, and writes an immutable audit record for every mutation. The Orchestrator validates requests against quota and policy, then persists an Environment desired-state record and exposes a trackable operation. The Placement service selects a datacenter and node pool by matching the requested flavor against live capacity, data-locality hints, and reservation policies — mirroring OCM's decoupled placement module [10]. The Inventory & Usage service maintains the hardware catalogue that cod hw list renders, aggregating capacity snapshots the agents report, and meters GPU-hours per tenant for chargeback — the single most effective incentive against resource hoarding [5].

D3

Debate: Push (central kubeconfigs) vs Pull (in-DC agents)

✓ Pull — agent in each DC (chosen)
  • Only outbound spoke→hub connectivity needed; works through DC firewalls and NAT without inbound holes [10].
  • Hub holds no cluster-admin credentials for any DC — a hub compromise cannot directly seize datacenters.
  • Agents keep reconciling autonomously during hub outages; proven to scale to thousands of clusters (the kubelet pattern, re-applied) [10].
  • DC admins can audit and sever the agent locally (“white-box” trust model, double opt-in registration) [10].
✗ Push — hub connects to every DC API server
  • Simpler to prototype: one service, N kubeconfigs, no agent rollout.
  • But it centralizes god-mode credentials, requires inbound network paths to every DC, floods the hub with watch events at scale — the KubeFed v2 architecture that the community abandoned [10].
  • Hub outage = total provisioning outage; no local autonomy.
Verdict

Pull. The agent doubles as the installer/upgrader of the per-DC stack (Capsule, vCluster operator, Kueue, GPU Operator MIG profiles, OPA policies, DCGM), so “adding a datacenter” reduces to: deploy agent → double opt-in registration → agent converges the DC to the platform baseline and starts reporting inventory. For interactive hub→DC needs (log streaming, debugging), a konnectivity-style reverse tunnel can be added later exactly as OCM's cluster-proxy does [10].

05 · Interface Contract

API Design: Imperative REST vs Declarative Control Plane

The API is where two philosophies collide. Imperative REST (“do this now, give me an operation ID”) is familiar to every integrator. Declarative reconciliation (“here is my desired state, converge to it”) is what makes Kubernetes itself robust [11]. ClusterOnDemand should refuse to pick just one.

D4

Debate: What is the source of truth — a REST service with a database, or CRDs on a hub cluster?

✓ Declarative CRD core (hub K8s)
  • Reconciliation loops give self-healing and idempotency for free — an agent crash mid-provision simply re-converges; imperative sagas must hand-roll this [11].
  • Environment, TenantPolicy, DatacenterRegistration as CRDs get watch semantics, optimistic concurrency, RBAC, and audit from the K8s API machinery.
  • GitOps-ready: operators can manage fleet policy via Argo CD; Crossplane-style compositions become possible later.
  • Agents already speak Kubernetes — the hub→spoke contract is just CRs + status (the ManifestWork pattern) [10].
✗ Pure REST + Postgres service
  • Simpler mental model for non-K8s integrators; no etcd size limits; rich relational queries (usage reports, billing joins) are natural.
  • But you re-implement watches, conditions, retries, and drift detection by hand — precisely the machinery K8s already ships.
  • Researchers' requests (“give me 4 H100s”) are desired state; forcing them through imperative verbs loses that.
Verdict — hybrid façade

Run a small hub Kubernetes cluster whose CRDs are the system of record for desired state, reconciled by agents. Wrap it with a thin REST façade that translates POST /v1/environments into an Environment CR and exposes the async-operation pattern (202 + Location) that REST clients expect [12]. Keep Postgres beside it for what relational stores do best: users, audit trails, and metering records. Each layer does the job it is best at.

Resource model & the async operation pattern

Provisioning takes seconds (namespace) to minutes (vcluster) — too long to block an HTTP request. The API therefore follows the long-running-operation convention: mutating calls return 202 Accepted with a Location header pointing at an operation resource the client polls (or subscribes to via SSE/webhooks); errors use RFC 7807 problem details; cancels are idempotent DELETEs on the operation [12].

# Discovery
GET  /v1/datacenters                          # list DCs + health
GET  /v1/datacenters/{dc}/hardware            # pools, SKUs, MIG profiles, free capacity
GET  /v1/flavors                              # requestable units

# Environment lifecycle (mode: namespace | vcluster)
POST   /v1/environments                       # → 202 Accepted, Location: /v1/operations/{id}
GET    /v1/environments?owner=me
GET    /v1/environments/{env}
PATCH  /v1/environments/{env}                 # scale up/down = update desired resources → 202
DELETE /v1/environments/{env}                 # → 202, grace period, idempotent
GET    /v1/environments/{env}/kubeconfig      # short-lived, OIDC-bound credentials
GET    /v1/environments/{env}/usage           # GPU-hours, storage, live utilization

# Operations (LRO)
GET    /v1/operations/{id}                    # pending | provisioning | ready | failed + steps

# Example create body
{
  "name": "llm-ablation",
  "mode": "namespace",
  "datacenter": "auto",                       # or pin: "dc-eu-west"
  "resources": {
    "flavors": { "gpu.h100.mig-3g": 4, "cpu.xeon.large": 2 },
    "storage": { "ion-nvme-fast": "20Ti" }

D4. Environment lifecycle state machine. Every state transition is emitted as an event on the operation resource and as a status condition on the Environment CR — the CLI's --watch and the REST poller read the same truth.

06 · Primary Interface

CLI Design: cod

The CLI is the product's face. Following the Command Line Interface Guidelines: human-first output with machine-readable escape hatches, noun-verb consistency, helpful errors, confirmation for destructive acts, and composability with the Unix ecosystem [13].

D5

Debate: Standalone binary vs kubectl plugin

✓ Standalone cod binary (chosen)
  • Talks to the hub REST API, not to any one cluster — discovery and placement span datacenters, which kubectl's single-context model handles poorly.
  • Owns the full auth journey (OIDC device flow on headless SSH boxes) and can render rich, task-oriented UX: progress, next-step hints, capacity tables.
  • Single static Go binary (Cobra) — trivial install on researcher laptops and login nodes.
✗ kubectl plugin (kubectl cod …)
  • Zero-install familiarity for K8s-native users and krew distribution.
  • But it inherits kubeconfig-context confusion, cannot cleanly express cross-DC discovery, and makes the REST API a second-class citizen.
Verdict

Standalone binary — but it must end every successful provision by writing a kubeconfig (cod kubeconfig ENV --merge), because after provisioning the researcher's daily driver is plain kubectl/helm/IDE tooling against their environment. The CLI creates worlds; kubectl lives in them.

Command grammar

cod login                                    # OIDC device flow → token cached in keyring
cod dc list                                  # datacenters + health + headline capacity
cod hw list --dc dc-eu-west --gpu            # F1: browse pools, SKUs, MIG profiles, free units

cod env create llm-ablation --mode namespace \
    --flavor gpu.h100.mig-3g=4 --flavor cpu.xeon.large=2 \
    --storage ion-nvme-fast=20Ti --ttl 14d --watch
  ↳ Placement: dc-eu-west · pool a100-mig · quota OK (4/16 GPU units used)
  ↳ Provisioning ████████░░ 80%  [tenant · rbac · netpol · quota · kueue-queue]
  ✔ Ready in 8s — next: cod kubeconfig llm-ablation --merge

cod env list -o json | jq '.[].status'       # F3: machine-readable by design
cod env scale llm-ablation --flavor gpu.h100.mig-3g=8   # F4: upscale (202 → watchable)
cod env scale llm-ablation --flavor gpu.h100.mig-3g=2   # F4: downscale
cod env delete llm-ablation                  # F5: prompts; --yes for scripts; idempotent
cod kubeconfig llm-ablation --merge          # F6: short-lived creds into ~/.kube/config
cod quota · cod usage --since 30d            # N4: my limits · my GPU-hours
cod env create … --dry-run                   # show placement + cost, change nothing

Conventions applied from the guidelines [13]: human-readable tables on stdout by default with -o json|yaml|wide for scripts; diagnostics to stderr; meaningful exit codes (0 ok, 2 quota exceeded, 3 capacity unavailable, 4 auth); --help everywhere with examples first; suggestions on typos; confirmation prompts for destructive verbs with --yes override; flags echo env vars (COD_DC, COD_OUTPUT) and a ~/.config/cod/config.yaml; shell completion for bash/zsh/fish. Long operations always print what to run next — the “conversation” principle.

07 · Lifecycle Flows

End-to-End Flows

The flow below traces the flagship use case — cod env create in namespace mode — across every component. The scale and delete flows reuse the same machinery with a different desired-state diff.

D5. Create flow (namespace mode). In vcluster mode the agent instead instantiates a vCluster helm release inside a host namespace and waits for its API server to answer before reporting Ready — roughly one minute instead of seconds.

Scale & delete reuse the same loop

Upscale/downscale is a PATCH that rewrites the resource envelope: the agent widens or narrows the Capsule tenant quota and Kueue ClusterQueue nominal quota. Downscaling below current usage doesn't kill pods immediately — quota blocks new admissions while a grace policy (cordon → preempt lowest-priority jobs after warning) converges actual usage; this mirrors how preemption-based fairness works in GPU schedulers [5] [9]. Delete flips the CR's deletion timestamp: the agent drains workloads with a grace period, deletes namespaces (cascading PVC deletion under reclaim-Delete storage classes), releases MIG slices, and reports final usage for the metering ledger before the record is tombstoned.

Failure honesty

Two failure classes deserve first-class UX: capacity misses (placement finds no pool with 4 free mig-3g slices — return alternatives: another DC, a smaller flavor, or a queue position) and partial provisions (netpol applied, quota failed — the reconciler retries idempotently and the operation shows exactly which step is stuck rather than a generic error). Both fall naturally out of the declarative core; both are painful to bolt onto a fire-and-forget imperative design.

08 · Governance

The Layered Isolation & Governance Stack

No single mechanism isolates a tenant. Effective GPU multi-tenancy is a stack, where each layer catches a different failure class [5]. ClusterOnDemand's agent installs and enforces every layer as part of the datacenter baseline.

D6. Five-layer isolation stack, synthesized from the Kubernetes multi-tenancy guidance and GPU tenant-isolation practice [1] [5].

Observability, metering, and the economics of fairness

Every DC runs Prometheus with the NVIDIA DCGM exporter, giving per-GPU utilization, memory, temperature, power and PCIe bandwidth, scoped to tenant namespaces in Grafana dashboards [5]. The hub rolls these up (Thanos/Mimir) into the fleet view and into per-tenant GPU-hour ledgers. This is not bookkeeping vanity: shared clusters routinely show requests wildly above usage (90% requested vs 30% used is commonly reported), and the documented cure is showing teams the cost of what they hold — chargeback converts hoarding into right-sizing [5]. Complementary levers: TTLs with renewal on research environments, idle detection (zero GPU utilization for N days → notify → sleep), and Kueue's borrowing so unused quota flows to whoever has queued work — the mechanism that pushes fleet utilization far above the ~40% baseline of naive sharing [5] [9].

Identity & credential flow

Researchers authenticate to the hub with institutional OIDC. The kubeconfigs that cod kubeconfig emits carry short-lived, tenant-scoped credentials — an OIDC exec plugin rather than long-lived static tokens — pointing at the DC's API endpoint (via capsule-proxy, which additionally filters cluster-scoped listings like namespaces so tenants only see their own) or at the tenant's vCluster endpoint. RBAC bindings are generated from the environment's member list, and regular automated audits of bindings guard against the gradual cross-tenant permission drift that plagues long-lived shared clusters [5] [6].

D6

Debate: Kubernetes-native self-service vs a Slurm-style batch queue

A serious counter-proposal for a research datacenter is: skip tenancy altogether and run one big Slurm (or Volcano-only) batch queue — researchers submit jobs, not clusters. It maximizes packing for pure training workloads, and academics already know sbatch [14]. But it fails three of your stated requirements: researchers explicitly want their own cluster/namespace (interactive services, notebooks, inference endpoints, custom stacks — things Slurm handles poorly); all datacenters already run Kubernetes; and a job queue cannot express “upscale my environment.” The synthesis is to treat batch scheduling as a layer inside ClusterOnDemand (Kueue/KAI at the platform level, optional Slurm-on-K8s such as Soperator inside a Tier-2 tenant cluster for die-hard HPC groups) rather than as the platform itself [14].

D7

Debate: Build thin, assemble OSS — or buy a platform?

✓ Thin CoD layer over OSS blocks (recommended)
  • ~80% of the machinery already exists as proven OSS: Capsule, vCluster, Kueue, GPU Operator, DCGM, OPA, OCM patterns. CoD's unique value is the glue: global catalogue, placement, quota policy, metering, and the cod UX.
  • No per-GPU licensing at H100 fleet scale; full control of the researcher experience; each block replaceable as the ecosystem moves (e.g., DRA).
✗ Buy (Run:ai, vCluster Platform, Rancher…)
  • Faster time-to-value, vendor support, hardened UI — real advantages for a small platform team.
  • But you'd still build the research-specific catalogue/CLI on top, now against a vendor API; license costs scale with the GPU count, which is exactly where you're rich.
Verdict

Build the thin layer; let OSS carry the weight. Re-evaluate commercial platforms only if the team cannot staff the glue — and check existing NVIDIA AI Enterprise entitlements first, since H100/H200 purchases often bundle Run:ai licenses [9].

10 · Synthesis

Recommended Blueprint & Phased Roadmap

Collecting every verdict into one stack: a pull-based hub-spoke management plane, tiered tenancy with namespace mode as the default, MIG-first GPU sharing, Kueue fairness, and a clig.dev-compliant CLI over a hybrid declarative/REST API.

TIER 1Namespace environment

Capsule Tenant + RBAC + default-deny netpol + aggregated quota + Kueue queue + PSS/OPA. Ready in seconds. The default for every researcher and the utilization workhorse.

TIER 2Virtual cluster

vCluster in a host namespace: own API server, etcd, CRDs, operators, K8s version. Pods still bin-pack on shared GPU pools. For teams needing control-plane autonomy.

TIER 3Hosted CP + dedicated nodes

Kamaji TenantControlPlane + reserved node pool. Operator-approved only: regulated data, kernel-level tuning, hard SLOs. Not self-service by default.

Open questions worth settling early

Four items deliberately left open: (1) quota currency — count-based (GPU units) is simple, GPU-hour budgets align better with research grants; a hybrid (concurrent cap + monthly hours) is likely. (2) Data gravity — petabyte datasets pin placement; the catalogue should eventually model dataset locality, not just silicon. (3) Interconnect-aware placement — NVLink/InfiniBand topology matters for multi-node training; start by exposing h100-sxm pools as indivisible topology blocks. (4) Sovereignty of the hub — run the hub in one DC with warm standby in another; agents' autonomy already covers short hub outages [10].

One-paragraph summary

ClusterOnDemand = a thin, opinionated global control plane: a hub that knows the hardware, the people, and the rules; agents that make each Kubernetes datacenter converge on declared tenant environments; namespace-based tenancy as the utilization-maximizing default with virtual clusters as the escape hatch; MIG and queue-based fairness turning expensive GPUs into a liquid, meterable commodity; and a CLI whose job is to make “give me 4 H100 slices for two weeks” a ten-second conversation.
