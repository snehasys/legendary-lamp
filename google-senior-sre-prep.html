The 6 Coding Patterns Google SRE Tests

1. Streaming I/O

Process multi-GB files without exceeding memory limits. Use iterators, generators, and line-by-line processing. Never load entire files into memory.

2. Concurrency & Rate Limiting

Hit 100+ endpoints with strict timeouts and rate limits. Use asyncio, thread pools, or goroutines. Enforce backpressure.

3. Log Parsing & Aggregation

Parse structured/unstructured logs. Extract patterns with regex. Aggregate by time windows, status codes, endpoints.

4. Defensive Error Handling

Handle malformed input, network timeouts, partial failures. Never crash silently. Always have retry logic with exponential backoff.

Key signals: Do you use a semaphore for concurrency control? Do you handle connection errors gracefully? Do you report partial results?

The Prompt"Given a stream of events from millions of hosts, detect anomalies in rolling 5-minute windows. An anomaly is when a host's error rate exceeds 3x the fleet average."

What they're testing: Streaming data structures (deque for windows), statistical reasoning, memory-bounded computation, real-time processing.

Problem 4: Implement a Token Bucket Rate Limiter

The Prompt"Implement a token bucket rate limiter that supports burst traffic. It should allow N requests per second with a burst capacity of B."

What they're testing: Understanding of rate limiting algorithms, time-based logic, thread safety, clean API design.

Problem 5: File Metadata Aggregator

The Prompt"Write a script that traverses a directory tree, groups files by extension, and reports total size per extension. Handle symlinks without infinite loops."

What they're testing: os.walk, symlink detection, aggregation patterns, edge case handling (broken symlinks, permission errors).

Solution Templates (Python)

Template: Streaming Log Parser (O(1) Memory)

#!/usr/bin/env python3
"""Parse a multi-GB log file with bounded memory."""
import re
from collections import Counter
import heapq

def parse_logs(filepath, top_n=10):
    # Pattern for common log format
    pattern = re.compile(
        r'(?P<ip>\S+) .* "(?P<method>\w+) (?P<path>\S+) .*" (?P<status>\d{3}) (?P<size>\d+)'
    )
    error_counts = Counter()

    # Stream line-by-line — never loads full file into memory
    with open(filepath, 'r', buffering=8192) as f:
        for line in f:  # iterator, O(1) memory per line
            match = pattern.search(line)
            if not match:
                continue  # skip malformed lines gracefully
            status = int(match.group('status'))
            if 500 <= status < 600:
                endpoint = match.group('path').split('?')[0]  # strip query params
                error_counts[endpoint] += 1

    # Top-N using heap — O(n log k) instead of full sort
    return heapq.nlargest(top_n, error_counts.items(), key=lambda x: x[1])
Key Interview Signal
Narrate your choices: "I'm using a file iterator because it processes one line at a time, keeping memory constant regardless of file size. I'm using heapq.nlargest for top-N because it's O(n log k) — more efficient than sorting the entire Counter."

Template: Concurrent Health Checker with Rate Limiting

#!/usr/bin/env python3
"""Check health of N servers with concurrency + rate limiting."""
import asyncio
import aiohttp
from dataclasses import dataclass
from typing import List

@dataclass
class HealthResult:
    host: str
    healthy: bool
    latency_ms: float = 0
    error: str = ""

async def check_health(
    hosts: List[str],
    timeout_sec: float = 5.0,
    max_concurrent: int = 50,
    requests_per_sec: int = 50
) -> List[HealthResult]:
    results = []
    semaphore = asyncio.Semaphore(max_concurrent)
    # Token bucket via asyncio — refill every 1/rate seconds
    rate_limiter = asyncio.Semaphore(requests_per_sec)

    async def refill_tokens():
        while True:
            await asyncio.sleep(1.0 / requests_per_sec)
            try:
                rate_limiter.release()
            except ValueError:
                pass  # already at max

    async def check_one(session, host):
        await rate_limiter.acquire()
        async with semaphore:
            try:
                start = asyncio.get_event_loop().time()
                async with session.get(
                    f"http://{host}/healthz",
                    timeout=aiohttp.ClientTimeout(total=timeout_sec)
                ) as resp:
                    latency = (asyncio.get_event_loop().time() - start) * 1000
                    results.append(HealthResult(
                        host=host,
                        healthy=(resp.status == 200),
                        latency_ms=latency
                    ))
            except (asyncio.TimeoutError, aiohttp.ClientError) as e:
                results.append(HealthResult(
                    host=host, healthy=False, error=str(e)
                ))

    async with aiohttp.ClientSession() as session:
        refiller = asyncio.create_task(refill_tokens())
        tasks = [check_one(session, h) for h in hosts]
        await asyncio.gather(*tasks)
        refiller.cancel()

    return results
Key Interview Signal
"I'm separating concurrency control (semaphore limits in-flight requests) from rate limiting (token bucket limits requests per second). The timeout is enforced per-request via aiohttp's ClientTimeout, and I'm catching both timeout and connection errors to ensure partial failures don't crash the entire check."

Template: Token Bucket Rate Limiter (Thread-Safe)

#!/usr/bin/env python3
"""Thread-safe token bucket rate limiter."""
import time
import threading

class TokenBucket:
    def __init__(self, rate: float, burst: int):
        self.rate = rate        # tokens per second
        self.burst = burst      # max tokens (burst capacity)
        self.tokens = burst     # start full
        self.last_refill = time.monotonic()
        self.lock = threading.Lock()

    def _refill(self):
        now = time.monotonic()
        elapsed = now - self.last_refill
        new_tokens = elapsed * self.rate
        self.tokens = min(self.burst, self.tokens + new_tokens)
        self.last_refill = now

    def acquire(self, tokens: int = 1) -> bool:
        """Try to consume tokens. Returns True if allowed."""
        with self.lock:
            self._refill()
            if self.tokens >= tokens:
                self.tokens -= tokens
                return True
            return False

    def wait(self, tokens: int = 1):
        """Block until tokens are available."""
        while not self.acquire(tokens):
            time.sleep(1.0 / self.rate)
Common Coding Round Traps
1. Loading entire file into memory with .read() or .readlines() — instant fail signal.
2. No error handling — production code must handle malformed input gracefully.
3. Ignoring timeouts in network code — shows you haven't operated production systems.
4. Over-optimizing algorithm before getting a working solution — correctness first, then optimize.
5. Not explaining your choices — narration is 50% of the signal.
Section 03 — Linux & Systems

Linux Internals & Kernel Reasoning

Google SRE interviews test mechanistic understanding of Linux — not command memorization. They want to know WHY you chose a command, WHAT signal you expect, and HOW the kernel handles the operation.

Process Management

Process states: Running (R), Sleeping (S), Uninterruptible Sleep (D), Zombie (Z), Stopped (T). The D-state is critical — it means the process is waiting on I/O and cannot be killed (even with SIGKILL).

Key concepts: fork/exec model, copy-on-write, process groups, sessions, orphan processes, zombie reaping.

Interview hot topic: "Why would a process be stuck in D-state?" — Answer: Waiting on uninterruptible I/O (disk, NFS mount). Indicates storage/network issue, not a process bug.

Memory Management

Virtual memory: Each process gets its own virtual address space. The kernel maps virtual pages to physical frames via page tables. The MMU handles translation.

Key concepts: Page cache, slab allocator, OOM killer, memory reclaim, swap, RSS vs VSZ, memory-mapped files, huge pages.

Interview hot topic: "The OOM killer triggered — how do you investigate?" — Check dmesg for OOM messages, identify the killed process, check /proc/meminfo for memory pressure.

File Systems & I/O

Inodes: Store metadata (permissions, timestamps, block pointers) — NOT the filename. Filenames live in directory entries that map name → inode number.

Key concepts: VFS layer, page cache, direct I/O, write-back vs write-through, journaling, inode exhaustion, file descriptors.

Interview hot topic: "Disk is full but df shows space" — Deleted files still held open by processes. Use lsof +D /path to find them.

Networking Internals

TCP handshake: SYN → SYN-ACK → ACK. The SYN backlog queue is finite — if saturated, new connections are dropped (SYN flood or misconfiguration).

Key concepts: Socket states, TIME_WAIT, connection pooling, TCP tuning (backlog, keepalive), DNS resolution, iptables/nftables, network namespaces.

Interview hot topic: "Intermittent connection timeouts" — Check SYN backlog (ss -s), check application thread pool, check DNS TTL, check for packet loss (mtr).

Scheduling & CPU

CFS (Completely Fair Scheduler): Uses a red-black tree of tasks sorted by virtual runtime. Tasks with less CPU time get priority. Nice values adjust weight.

Key concepts: Context switches, CPU affinity, cgroups CPU limits, load average (1/5/15 min), runqueue depth, CPU steal time (VMs).

Interview hot topic: "High load average but low CPU%" — Many processes in D-state (I/O wait) inflate load average without consuming CPU.

Cgroups & Containers

Cgroups v2: Hierarchical resource control — CPU, memory, I/O, PIDs. Prevents noisy neighbor problems. Containers use cgroups + namespaces for isolation.

Key concepts: Memory limits (hard/soft), CPU shares vs quotas, I/O weight, PID limits, OOM within cgroup, namespace types (PID, NET, MNT, UTS, IPC, USER).

Interview hot topic: "How do cgroups prevent noisy neighbors?" — Memory cgroup enforces hard limits; CPU cgroup uses CFS bandwidth throttling; I/O cgroup uses BFQ weights.

Google doesn't evaluate command knowledge. They evaluate judgment through command choice. Before touching the keyboard, strong SREs ask: Is this live or historical? Am I looking for symptoms or root cause? What's the lowest-cost, highest-signal command?

Google's Googleyness & Leadership round evaluates six specific attributes. It's not a casual chat — it's a scored signal that goes directly to the Hiring Committee. For SRE specifically, they weight incident leadership, blameless culture, and calm under pressure.

Section 05 — System Design

NALSD: Non-Abstract Large System Design

The NALSD round is the defining round of Google SRE interviews. Unlike abstract system design, you work with real physical constraints — bandwidth, IOPS, storage, latency budgets. You must produce a "Bill of Materials" with actual numbers.

The NALSD Framework (8 Steps)

1. Clarify Requirements & Constraints

Ask: What's the SLO? What's the data volume? What's the latency budget? What's the recovery time objective (RTO)?

2. Estimate Load Characteristics

QPS, storage growth rate, read/write ratio, peak-to-average ratio. Use back-of-envelope math.

3. Choose Architecture Pattern

Active-active vs active-passive, sharding strategy, replication model, consistency requirements.

4. Capacity Math (Bill of Materials)

Calculate: How many servers? How much storage? What network bandwidth? What IOPS per disk?

5. Identify Failure Modes

Single points of failure, blast radius, cascading failures, split-brain scenarios, data loss windows.

6. Design for Degradation

What happens at 2x load? At 10x? What do you shed first? How does the system degrade gracefully?

7. Observability & Alerting

SLIs to measure, burn-rate alerting, dashboards, what gets paged vs. what gets a ticket.

8. Operational Concerns

Deployment strategy, rollback plan, capacity planning, disaster recovery, cost optimization.

Common NALSD Questions

Design a Global Metrics Pipeline

Must address: fan-in from millions of hosts, sharding by metric name, backpressure when ingestion exceeds capacity, cardinality explosions, HA ingestion, query latency SLO.

Design Disaster Recovery for 5PB

Must address: RTO/RPO constraints, bandwidth math (can you replicate 5PB in 4 hours?), incremental vs full backup, cost of hot standby vs cold restore.

Design a Feature Flag System

Must address: atomic rollout, blast-radius control (1% → 10% → 100%), auditability, rollback safety, config distribution consistency, staleness tolerance.

90-Day Plan for a Flaky Service

Must address: immediate stabilization (Week 1), SLO definition (Week 2-3), observability gaps (Week 3-4), toil reduction (Week 5-8), systemic fixes (Week 8-12).

NALSD Trap: The Physics Check
A candidate designed active-passive DR for 5PB with a 4-hour RTO. The interviewer asked: "What's the bandwidth needed to replicate 5PB in 4 hours?" Answer: 5PB / 4h = 1.25 PB/h = ~2.8 Tbps. That's physically impossible on standard links. The candidate failed for not checking the physics. Always validate your design against physical limits.
Section 06 — Troubleshooting

The Troubleshooting Round

This round mirrors real incidents. You're given a vague symptom and must systematically narrow down the cause. The #1 rule: MITIGATE FIRST, then diagnose. Interviewers fail candidates who jump to root cause before stabilizing.

The Troubleshooting Framework

Step 1: Assess Impact

How many users affected? Which regions? Is it getting worse? What's the error budget burn rate? This determines urgency and whether to page more people.

Step 2: Mitigate

Can we drain traffic? Roll back a deploy? Increase capacity? Failover to another region? Stabilize the patient before diagnosing the disease.

Step 3: Hypothesize

Form 2-3 hypotheses ranked by likelihood. "Given the symptoms, it could be: (1) deploy regression, (2) dependency failure, (3) capacity exhaustion."

Step 4: Test & Narrow

Choose the highest-signal, lowest-cost test for each hypothesis. Eliminate possibilities systematically. Don't scattershot commands.

Classic Troubleshooting Scenarios

Scenario: "The site is slow. CPU is normal."

Strong answer flow:

1. tail -n 200 /var/log/app.log — check for recent errors/timeouts
2. ss -s — check connection states (TIME_WAIT accumulation? SYN backlog?)
3. iostat -x 1 3 — check disk I/O wait (the silent latency killer)
4. vmstat 1 5 — check for memory pressure (si/so columns)
5. Only then form hypotheses: "Based on high await in iostat, I suspect disk I/O contention. Let me check which process is generating the I/O with iotop."

Scenario: "p99 latency doubled after a deploy"

Strong answer flow:

1. Mitigate: "First, is this within error budget? If not, I'd recommend immediate rollback while we investigate."
2. Correlate: "What changed in the deploy? I'd diff the release, check for new dependencies, config changes."
3. Canary analysis: "If we have canary metrics, compare canary vs baseline latency distribution."
4. Drill down: "Check if latency increase is uniform or concentrated in specific endpoints/regions."
5. Trace: "Pull distributed traces for slow requests — where is the time being spent?"

Scenario: "A service can't reach its database"

Layer-by-layer diagnosis:

1. DNS: dig db-host.internal — Does it resolve? Is the IP correct?
2. Network: nc -zv db-host 5432 — Can we establish a TCP connection?
3. TLS: openssl s_client -connect db-host:5432 — Certificate valid? Not expired?
4. Auth: Check connection string, credentials, IAM roles
5. Capacity: SELECT count(*) FROM pg_stat_activity — Connection pool exhausted?
6. Firewall: Check security groups, iptables rules, network policies

Section 07 — Test Yourself

Rapid-Fire Quiz

Test your knowledge across all interview dimensions. Each question mirrors real Google SRE interview patterns.

Q1: A process is in D-state (uninterruptible sleep). What does this mean?
D-state means the process is in uninterruptible sleep, typically waiting on disk I/O or an NFS mount. It cannot be killed because the kernel needs the I/O operation to complete to maintain filesystem consistency. Many D-state processes usually indicate a storage or network filesystem issue.
Q2: You're writing a Python script to process a 50GB log file. Which approach is correct for memory efficiency?
Using for line in f treats the file object as an iterator, reading one line at a time with O(1) memory usage regardless of file size. The other options either load the entire file into memory (.read(), .readlines()) or use mmap which maps the entire file into virtual address space (works but isn't the idiomatic Python approach for line-by-line processing).
Q3: Your service has a 99.9% availability SLO. How much downtime does that allow per month?
99.9% availability = 0.1% downtime. 30 days × 24 hours × 60 minutes = 43,200 minutes/month. 0.1% of 43,200 = 43.2 minutes. This is your error budget — once consumed, you should freeze deployments and focus on reliability.
Q4: In a Google SRE troubleshooting interview, what should you do FIRST when told "the site is down"?
The "Mitigation-First" mindset is the #1 signal Google evaluates. Before debugging, assess: How many users are affected? Can we mitigate (drain traffic, rollback, failover)? Stabilize the patient before diagnosing the disease. Jumping straight to root-cause analysis is a common failure pattern.
Q5: What distinguishes a "process question" from an "experience question" in the Googleyness round?
This is the most common mistake in Googleyness rounds. Experience questions want depth in ONE specific story (use STAR). Process questions want your FRAMEWORK for a category of situations — start with principles/approach, then briefly illustrate with an example. Answering both with just a story leaves signal on the table.
Q6: You see high load average but CPU utilization is low. What's the most likely cause?
Linux load average counts ALL processes in the run queue, including those in D-state (waiting on I/O). If many processes are blocked on disk I/O or NFS, load average rises without CPU consumption. Check with vmstat (wa column) or cat /proc/loadavg and compare with mpstat CPU idle%.
Q7: In NALSD, you need to replicate 5 PB of data with a 4-hour RTO. What minimum bandwidth is required?
5 PB = 5,000 TB = 40,000 Tb. Divide by 4 hours = 10,000 Tb/h = ~2,778 Gbps ≈ 2.8 Tbps. This exceeds what's physically achievable on standard links, which means the design must use incremental replication, pre-staged warm standby, or accept a longer RTO. This is the "physics check" that catches candidates in NALSD.
Q8: What is the correct SRE approach to "toil"?
Google defines toil as work that is manual, repetitive, automatable, tactical, without enduring value, and scales linearly with service growth. The SRE charter targets keeping toil below 50% of an SRE's time. The goal is to automate toil away, freeing engineers for reliability engineering work.
Q9: Which concurrency pattern is most appropriate for checking health of 100,000 servers with a rate limit?
asyncio is ideal for I/O-bound concurrent work (network requests). A Semaphore limits concurrent in-flight requests (e.g., 50-100 at a time), while a separate token bucket enforces the rate limit (requests/second). This gives you high throughput with bounded resource usage. Spawning 100K threads would exhaust OS resources.
Q10: In the behavioral round, what does "blamelessness" mean for SRE stories?
Blameless culture is core to Google SRE. In interviews, frame outages as system failures: "The deployment pipeline lacked a canary stage" not "Bob pushed bad code." Focus on contributing factors, what the system allowed to happen, and systemic changes you drove to prevent recurrence. This signals operational maturity.

In Python, I'd open the file and iterate line by line using a for loop over the file object — this uses the file as an iterator with O(1) memory per line. For the aggregation, I'd use a Counter or defaultdict to accumulate results, which stays bounded by the number of unique keys, not the file size. If even the aggregation could grow unbounded — say millions of unique endpoints — I'd use a heap to maintain only the top-N results. I'd also add error handling for malformed lines and use buffered I/O for performance. The key insight is separating the streaming read from the bounded aggregation."

Implement a rate limiter. Walk me through your design choices. +

"I'd implement a token bucket because it naturally handles burst traffic while enforcing a long-term rate. The bucket has two parameters: rate (tokens per second) and burst (maximum tokens). Tokens refill continuously at the rate, and each request consumes one token. If the bucket is empty, the request is rejected. For thread safety, I'd use a lock around the refill-and-consume operation. The refill is lazy — I calculate elapsed time since last access and add proportional tokens, capped at burst size. This avoids needing a background refill thread. The alternative is a sliding window counter, which is simpler but doesn't handle bursts as gracefully."

You need to check health of 100,000 servers. How do you structure this? +

"This is an I/O-bound problem, so I'd use asyncio rather than threads or multiprocessing. I'd create an async function that hits each server's health endpoint with a strict timeout — say 5 seconds. To avoid overwhelming the network or target servers, I'd use two controls: a Semaphore limiting concurrent in-flight requests to maybe 100, and a separate token bucket enforcing the requests-per-second rate limit. I'd collect results into a list of dataclass objects with host, status, latency, and any error message. Partial failures are expected — a timeout or connection error for one host shouldn't affect others. Finally, I'd aggregate results: how many healthy, how many timed out, how many errored, and flag any hosts with latency above a threshold."

Tell me about the most severe outage you handled. +

"At my previous company, we had a cascading failure that took down our payment processing service during peak Black Friday traffic — affecting roughly 50,000 transactions per minute. I was the incident commander. My first action was mitigation: I coordinated draining traffic to our secondary region within 3 minutes, which restored service for 80% of users. Only then did we diagnose — the root cause was a connection pool exhaustion triggered by a slow downstream dependency that had deployed a change without our knowledge. After stabilization, I led the postmortem. We identified three systemic gaps: no circuit breaker on that dependency, no alerting on connection pool saturation, and no cross-team deploy notification. I drove all three action items to completion over the next sprint. The result was MTTR for similar incidents dropped from 45 minutes to under 5 minutes, and we established a cross-team deploy calendar that prevented blind-side failures."

How do you influence teams without formal authority? +

"My approach has three pillars. First, I lead with data — I quantify the reliability impact in terms the other team cares about, whether that's user-facing errors, revenue impact, or engineering time lost to incidents. Second, I build credibility by offering help before asking for change — I might write the first draft of an SLO, build a dashboard for them, or help debug their on-call issues. Third, I find shared incentives — reliability improvements often align with the other team's goals if framed correctly. For example, I recently needed a platform team to add circuit breakers to their client library. Instead of filing a bug, I showed them data on how cascading failures from their service were causing pages for three downstream teams, wrote a design doc with the proposed solution, and offered to pair on the implementation. They shipped it in two weeks because it also reduced their own on-call burden."

Describe a time you received critical feedback. How did you respond? +

"During a performance review, my manager told me that while my technical contributions were strong, I wasn't making my work visible enough to leadership, and I tended to solve problems alone rather than bringing others along. My initial reaction was defensiveness — I felt the work should speak for itself. But I took a day to reflect and realized the feedback was accurate. I started three practices: writing brief weekly summaries of reliability wins for my skip-level, actively pulling junior engineers into my projects as collaborators rather than just reviewers, and presenting postmortem findings at our engineering all-hands. Within two quarters, I was recognized in our team's impact review, and two of the junior engineers I'd mentored took on independent on-call rotations. The feedback fundamentally changed how I think about impact — it's not just what you build, it's whether others can learn from and build upon your work."

Tell me about a time you disagreed with a software engineer about a reliability concern. +

"A feature team wanted to launch a new real-time notification system without a circuit breaker or graceful degradation path. Their argument was that the feature was low-risk and the deadline was tight. I disagreed because the notification system depended on three external services, any of which could cause cascading latency. Rather than blocking the launch, I proposed a compromise: launch with a feature flag at 5% rollout, add basic timeout handling which I offered to implement myself, and define an SLO together so we'd have objective criteria for when to pause the rollout. They agreed because I wasn't saying 'no' — I was saying 'yes, safely.' We launched, caught a latency issue at 5% that would have been a full outage at 100%, fixed it, and rolled out fully the following week. The relationship with that team actually improved because they saw SRE as an enabler rather than a blocker."

How do you handle being paged at 3AM for an alert you've never seen? +

"First, I check the alert description and runbook link — well-operated services should have runbooks for every alert. If there's a runbook, I follow it. If not, I assess impact: is this user-facing? What's the error rate? Is it getting worse? If impact is significant and growing, I escalate immediately — I'd rather wake someone with context than spend 30 minutes floundering alone. If impact is contained, I start systematic diagnosis: check recent deploys, check dependency health, check resource utilization. I document everything I find in the incident channel as I go. After resolution, I always file two things: a runbook for this alert if one didn't exist, and a postmortem if the incident was significant. The meta-principle is: at 3AM, your job is to mitigate and escalate, not to be a hero. Heroics at 3AM lead to mistakes."

Second, the SRE culture itself — Google literally wrote the book on SRE, and the principles of error budgets, blameless postmortems, and toil elimination aren't just aspirational there, they're operational reality with organizational support. Third, impact — when you improve reliability at Google's scale, you're improving the experience for billions of users. A 10ms latency reduction or a 0.01% availability improvement translates to millions of better user experiences per day. That kind of leverage is what motivates me as an engineer."

Coding Round Checklist

Always: Stream files (never .read()), handle errors gracefully, use timeouts for network calls, explain your choices out loud, validate with test cases.

Patterns: Counter for aggregation, heapq for top-N, deque for sliding windows, asyncio.Semaphore for concurrency, generators for streaming.

SRE Concepts (Must Know Cold)

SLI: What you measure (latency, error rate)
SLO: Your target (99.9% < 200ms)
Error Budget: 1 - SLO (your allowed unreliability)
Burn Rate: How fast you consume error budget
Toil: Manual, repetitive, automatable work (target <50%)
MTTR: Mean Time To Recovery
MTTD: Mean Time To Detection
Blast Radius: Scope of failure impact
Circuit Breaker: Stop calling a failing dependency
Backpressure: Signal upstream to slow down

Troubleshooting Framework

Order of operations:
1. Assess impact (scope, severity, trend)
2. Mitigate (drain, rollback, failover)
3. Hypothesize (2-3 ranked possibilities)
4. Test (highest-signal, lowest-cost first)
5. Fix (root cause after stabilization)
6. Prevent (postmortem, systemic changes)

Never: Jump to root cause before mitigating, scattershot commands without hypothesis, blame individuals.
