Round 1 — 60 Minutes

Agentic Coding Round

A coding interview where you implement a single problem with multiple extensions, using your preferred IDE and AI tools. This tests how you actually build software in 2026 — with AI as your copilot.

What Makes This Different

Unlike traditional LeetCode interviews, Reflection's Agentic Coding round mirrors real engineering work. You use your own IDE, your preferred language, and any AI tools you want (Copilot, Cursor, Claude, etc.). The emphasis is on how you think, iterate, and extend — not whether you memorized an algorithm.

The problem starts simple and grows in complexity. Each extension tests whether you can adapt your initial design. Interviewers watch for: Do you refactor when needed? Do you recognize when your initial approach won't scale? Do you use AI tools strategically rather than blindly?

Critical Setup — Do This Before the Interview
Have your IDE ready, language installed, AI tools configured, and verify you can compile and run code while screen-sharing. Test your screen share setup. Nothing kills momentum like 10 minutes of setup debugging.

Sample Problem 1: Rate Limiter

Part A: Implement a rate limiter that allows at most N requests per second for a given user ID.

Part B: Extend it to support sliding window (not just fixed windows).

Part C: Make it distributed — multiple instances need to coordinate. Discuss trade-offs between consistency and availability.

Model Approach

Start with a simple token bucket or fixed-window counter using a dictionary. For Part B, implement a sliding window log or sliding window counter hybrid — explain that the log approach is precise but memory-heavy, while the counter approach approximates but is O(1) space per user. For Part C, discuss Redis-based centralized state vs. local approximation with periodic sync. Articulate the CAP trade-off: strict consistency requires coordination (latency cost), while eventual consistency may briefly over-allow requests.

Sample Problem 2: Task Scheduler for Async Jobs

Part A: Build a simple task queue that processes jobs in FIFO order with configurable concurrency.

Part B: Add priority levels and ensure high-priority tasks preempt lower ones.

Part C: Add retry logic with exponential backoff and a dead-letter queue for permanently failed tasks.

Model Approach

Use a priority queue (heap) with a worker pool. For concurrency, use asyncio or threading with a semaphore. When adding retries, wrap each task execution in a retry decorator with configurable max attempts and backoff multiplier. The dead-letter queue is just a separate collection that stores tasks exceeding max retries along with their failure metadata. Discuss: should retry count be per-task or per-task-type? What happens if the scheduler crashes mid-retry?

Sample Problem 3: Log Aggregation Pipeline

Part A: Parse structured log lines and compute per-endpoint latency percentiles (p50, p95, p99).

Part B: Handle streaming input — process logs as they arrive, maintaining running percentiles.

Part C: Add anomaly detection — flag endpoints whose p99 exceeds 2x their historical baseline.

Model Approach

For batch percentiles, sort and index. For streaming, use a t-digest or quantile sketch data structure — explain the trade-off between exact computation (requires storing all values) and approximate streaming algorithms (bounded memory). For anomaly detection, maintain an exponential moving average of historical p99 and compare incoming windows against it. Discuss: what window size balances responsiveness vs. noise?

Sample Problem 4: File Synchronization Engine

Part A: Given two directory trees (represented as nested dicts), compute the diff — files added, removed, modified.

Part B: Generate a minimal set of operations (copy, delete, move) to synchronize source to target.

Part C: Handle rename detection — if a file's content hash matches a deleted file, treat it as a rename rather than delete+add.

Model Approach

Represent each file as (path, content_hash, modified_time). Diff by walking both trees and comparing. For move detection, build a hash-to-path index for deleted files and check new files against it. Discuss: content hashing is expensive for large files — when would you use mtime-based shortcuts? How does this relate to how git detects renames?

Sample Problem 5: LRU Cache with TTL

Part A: Implement an LRU cache with O(1) get/put.

Part B: Add per-key TTL (time-to-live) — expired entries should be evicted.

Part C: Make it thread-safe with minimal lock contention. Discuss the trade-offs of different locking strategies.

Model Approach

Classic doubly-linked list + hashmap for LRU. For TTL, add expiry timestamps and lazily evict on access plus a background sweep for proactive cleanup. For thread safety, discuss: global lock (simple but contention), sharded locks (partition keyspace), or lock-free approaches with CAS operations. At Reflection's scale, sharded locks with consistent hashing give the best balance.

Pro Tips for This Round

1. Think aloud constantly. Narrate your reasoning: "I'm choosing a hashmap here because we need O(1) lookup by user ID..."

2. Start with the simplest correct solution. Don't over-engineer Part A. Get something working, then refactor when complexity demands it.

3. Use AI tools strategically. Let AI handle boilerplate while you focus on core logic and design decisions. Review what it generates.

4. When extending, pause and redesign if needed. It's a strength to say "My current approach won't cleanly support this — let me refactor."

5. Write at least one test. Even a simple assertion shows you care about correctness.

6. Discuss system-level trade-offs. This is Reflection — they care about how your code would behave at scale, under failure, in production.

Design Survey

Part 1: Breadth-of-Knowledge Survey (~25-30 min)

Rapid-fire assessment of your systems knowledge across domains critical to Reflection's infrastructure. Be concise but precise — give key numbers and trade-offs.

Networking

QuestionWhat a Strong Answer Covers
Explain the difference between InfiniBand and Ethernet for GPU cluster networking.InfiniBand: lossless fabric, RDMA-native, lower latency (~1-2μs), higher bandwidth (400Gb/s NDR), kernel bypass. Ethernet: ubiquitous, cheaper, requires RoCE for RDMA, higher latency (~5-10μs), but closing the gap with 800GbE.
What is RDMA and why does it matter for distributed training?Remote Direct Memory Access — allows one machine to read/write another's memory without involving the CPU or OS kernel. Eliminates context switches and copies. Critical for AllReduce operations where GPUs exchange gradients.
Explain NCCL and its role in distributed training.NVIDIA Collective Communications Library — optimizes multi-GPU collective operations (AllReduce, AllGather, Broadcast). Automatically selects optimal algorithms based on topology (ring, tree, hybrid). Uses NVLink intra-node and InfiniBand inter-node.
What is a fat-tree network topology and why is it used in GPU clusters?A Clos network providing full bisection bandwidth — any node can communicate with any other at full link speed simultaneously. Prevents bandwidth bottlenecks during AllReduce where all nodes communicate simultaneously.
What happens when there's network congestion during AllReduce?A single slow link creates a straggler effect — all nodes must wait at the synchronization barrier. Can reduce effective cluster throughput by 20-40%. Adaptive routing and congestion control (ECN, PFC) help mitigate.

GPUs & Hardware

QuestionWhat a Strong Answer Covers
Describe the H100 GPU architecture at a high level.Hopper architecture. 80GB HBM3 at 3.35 TB/s. 132 SMs with 4th-gen Tensor Cores (FP8). 900 GB/s NVLink (18 links). Transformer Engine for mixed-precision. 700W TDP. Key advance: FP8 Tensor Cores, 3x NVLink bandwidth vs A100.
What is NVLink vs PCIe for GPU communication?NVLink H100: 900 GB/s bidirectional (18 links). PCIe Gen5 x16: 128 GB/s. NVLink is ~7x faster. Used for intra-node GPU-to-GPU communication, critical for tensor parallelism.
Explain the memory hierarchy of a modern GPU training system.Registers → Shared Memory/L1 (~228KB/SM) → L2 Cache (50MB) → HBM (80GB, 3.35TB/s) → NVLink (peer GPU) → Host RAM via PCIe → Remote node via InfiniBand. Each level trades capacity for bandwidth/latency.
What are XID errors and why do they matter?NVIDIA GPU error codes. XID 79 = GPU off bus (PCIe failure). XID 48 = double-bit ECC (uncorrectable). XID 63 = row remapping failure. Indicate hardware degradation. Single XID can crash a multi-thousand-GPU job.
What is the Transformer Engine on H100?Hardware-accelerated dynamic precision management. Auto-selects FP8 vs FP16 per-layer based on tensor statistics. Maintains accuracy while doubling throughput vs FP16-only. Uses per-tensor scaling factors computed on-the-fly.

Data & Storage

QuestionWhat a Strong Answer Covers
How do you handle petabyte-scale training data pipelines?Distributed storage (Lustre/GPFS or S3). Prefetch and pipeline I/O with compute. Tokenization stored as memory-mapped files. Deduplication (MinHash). Quality filtering. Deterministic sharding for reproducibility.
What is checkpointing and what are the trade-offs?Periodically saving model state to persistent storage. Frequent = less lost work but more I/O overhead. Async checkpointing (local NVMe → background copy) minimizes interruption. At 1000+ GPUs, checkpoint size can be hundreds of GB.
How would you design a data deduplication pipeline?Multi-stage: exact dedup (hash), near-dedup (MinHash + LSH), URL-based, n-gram overlap. Trade-off: aggressive dedup improves quality but risks removing legitimate patterns. Typical threshold: ~80% Jaccard similarity.

Backend Infrastructure

QuestionWhat a Strong Answer Covers
Explain the different parallelism strategies for training large models.Data Parallel: replicate model, shard data, AllReduce gradients. Tensor Parallel: split layers across GPUs (NVLink). Pipeline Parallel: split model stages across nodes (micro-batching). Expert Parallel: MoE experts on different GPUs. Hybrid: TP within node + PP across nodes + DP across replicas.
What is FSDP/ZeRO and why is it important?Shards optimizer states (ZeRO-1), gradients (ZeRO-2), and parameters (ZeRO-3) across GPUs. Reduces per-GPU memory from O(model_size) to O(model_size/N). Enables training models that don't fit on a single GPU.
How does Kubernetes interact with GPU scheduling?Device plugins expose GPUs as schedulable resources. Challenges: topology awareness (NVLink co-location), gang scheduling, preemption policies, health monitoring. Many teams layer Slurm on top for ML-specific scheduling.
Design a model serving infrastructure for low-latency inference.Tensor parallel for large models. Continuous batching. KV-cache management. Speculative decoding. Load balancing with session affinity. Quantization (INT8/FP8). Metrics: TTFT, TPS, p99 latency.

Part 2: System Design Question (~30-35 min)

Open-ended design problem evaluating principled trade-offs, robustness, scalability, and clear communication.

Design 1: Distributed Training Job Scheduler

Requirements: Schedule training jobs across 1000+ GPUs. Gang scheduling. Handle node failures. Priority-based.

Model Approach

Core: priority queue of pending jobs + resource inventory. Gang scheduling needs atomic allocation. Components: (1) Resource Manager tracking GPU health/topology/allocation. (2) Scheduler with pluggable policies (FIFO, fair-share, priority). (3) Health Monitor for failure detection and job migration. (4) Checkpoint Coordinator for pre-preemption saves. Use replicated state machine (Raft) for scheduler state. Key trade-off: utilization (packing small jobs) vs. locality (keeping GPUs topologically close for NVLink). Implement topology-aware scheduling preferring same NVLink domain.

Design 2: Real-time Model Evaluation Pipeline

Requirements: Continuously evaluate checkpoints against benchmarks. Results within minutes. Hundreds of eval tasks in parallel. Handle failures.

Model Approach

Architecture: (1) Checkpoint Watcher monitors storage. (2) Eval Orchestrator fans out tasks to GPU workers. (3) Result Aggregator publishes to dashboard. Decouple eval from training (separate GPU pool). Use task queue (Ray) for distribution. Progressive evaluation — fast benchmarks first, slow ones only if fast pass threshold. Idempotent tasks with auto-retry. Trade-off: dedicating GPUs to eval reduces training throughput, but early detection of issues saves far more compute.

Design 3: Distributed KV Store for Model Weights

Requirements: Store/serve model weights (hundreds of GB). Fast reads for inference. Versioning. Optimize for sequential reads.

Model Approach

Tiered storage: hot (NVMe on inference nodes), warm (distributed object store), cold (archival). Memory-map weight files for zero-copy loading. Tensor-level sharding so each GPU loads only its shard. Content-addressed versioning (hash = version ID). Pre-shard at checkpoint time in expected inference layout. Trade-off: pre-sharding increases storage but eliminates reshape latency at load time — justified at scale.

Design Strategy

Drive the conversation. State assumptions, draw high-level architecture, then dive into the most interesting component. Always discuss: What fails? How do you detect it? How do you recover?

Scenario 1: The Silent Slowdown

Situation: A 512-GPU job has throughput degraded by 30% over 12 hours. No errors in logs. Job hasn't crashed.

Metrics: Throughput dropped 1200→840 samples/sec. 4 GPUs on node-37 at 72% util (others 95%). Node-37 temp: 83°C. NCCL p99 latency: 2ms→8ms.

Model Debugging Walkthrough

Hypothesis: The 4 GPUs on node-37 are thermal throttling. At 83°C, H100s begin throttling clocks, creating a straggler effect on AllReduce.

Validation: Check nvidia-smi -q -d CLOCK on node-37. If current clocks below base (e.g., 1.2 GHz vs 1.98 GHz), confirmed.

Root cause: Why hot? Check fan RPM, ambient temp (hot aisle?), workload imbalance, airflow obstruction.

Fix: Drain node-37, replace with spare, restart from checkpoint.

Platform improvement: (1) Temp alerts at 78°C (before throttling). (2) Auto straggler detection on collective latency. (3) Proactive node replacement on sustained thermal anomalies. (4) Throughput regression alerts vs. rolling baseline.

Scenario 2: The Mysterious NCCL Timeout

Situation: A 1024-GPU job crashes with "NCCL Watchdog Timeout" after 6 hours. Third time this week. Different rank each time.

[Rank 847] NCCL WARN Watchdog caught collective timeout on AllReduce
[Rank 847] Last enqueued collective: AllReduce (count=134217728, datatype=float16)
[Rank 847] Timeout after 600000ms
# All other ranks: "Connection closed by remote peer"
Model Debugging Walkthrough

Key insight: The rank reporting timeout is NOT the culprit — it's the one that noticed. The actual problem is the rank that went silent.

Step 1: Identify which ranks did NOT report timeout — those crashed/hung first.

Step 2: On silent ranks: check dmesg for XID errors, GPU memory errors, NVLink errors. Check if CUDA context alive. Check for SIGKILL from OOM killer.

Step 3: Different ranks each time → systemic issue. Possible: intermittent fabric issues (cable degradation), stochastic memory errors, race condition in training code.

Step 4: Check InfiniBand port error counters. Look for SymbolErrors, LinkDowned, RcvErrors correlating with crash times.

Platform improvement: (1) Pre-job NCCL benchmark on allocated nodes. (2) Continuous fabric monitoring with per-port error alerts. (3) Auto node quarantine after 2+ NCCL timeouts. (4) Per-rank heartbeat to identify first silent rank.

Scenario 3: Loss Spike After Checkpoint Resume

Situation: Job restarted from checkpoint. Loss immediately spikes from 2.3 to 8.7 and doesn't recover. Same checkpoint worked 2 days ago.

Metrics: Gradient norm 100x higher than pre-preemption. Learning rate matches schedule.

Model Debugging Walkthrough

Hypothesis 1 (most likely): Node topology changed. Job resumed on different nodes with different GPU-to-rank mapping. Model shards loaded onto wrong ranks (pipeline stage 3's weights on stage 1's GPU) → garbage forward pass.

Hypothesis 2: Optimizer state corruption — Adam momentum/variance not loaded correctly (all zeros = effective LR spike).

Hypothesis 3: Data pipeline state mismatch — dataloader resumed from wrong position.

Validation: Check rank-to-node mapping vs. original run. Verify tensor shapes/statistics match expected values.

Platform improvement: (1) Checkpoint validation before resume. (2) Topology-aware restart with consistent rank mapping. (3) Auto loss sanity check (halt if loss >2x pre-checkpoint within 100 steps). (4) Checkpoint integrity hashes.

Active Health Checking Design

If time allows, you'll discuss designing an active health checking system:

Passive vs. Active

Passive: Monitor existing signals (telemetry, logs). Low overhead, reactive.

Active: Run diagnostic workloads proactively. Higher overhead, catches issues earlier. Examples: NCCL benchmarks, memory stress tests, NVLink bandwidth checks.

When to Run

Pre-job: Quick health validation before allocation (GPU mem test, NVLink BW, NCCL all-reduce).

Inter-job: Deeper diagnostics between allocations (DCGM Level 3).

Periodic: Comprehensive stress tests during idle. Track trends to predict failures.

Model Answer

Three-tier system. Tier 1 (continuous, passive): GPU telemetry via DCGM — temps, power, ECC, clocks — alert on statistical anomalies. Tier 2 (pre-job, active): 60-second NCCL all-reduce benchmark on allocated nodes. Quarantine if bandwidth >10% below expected. Tier 3 (periodic, deep): DCGM Level 3 diagnostics during idle windows (12-min comprehensive test). Key trade-off: check thoroughness vs. GPU availability. Optimize: Tier 1 zero-overhead (piggyback on telemetry), Tier 2 fast (60s vs hours of training), Tier 3 only during genuine idle time.

10 questions across all interview dimensions. Click an answer to check — explanations revealed on selection.

1. What is the bidirectional NVLink bandwidth on an H100 GPU?
The H100 has 4th-generation NVLink with 18 links providing 900 GB/s total bidirectional bandwidth. This is 7x PCIe Gen5 x16 (128 GB/s) and 1.5x the A100's NVLink (600 GB/s).
2. In a 16,384-GPU cluster, what is the approximate Mean Time To Failure (MTTF)?
Meta's research shows MTTF of ~1.8 hours at 16,384 GPUs. At 1,024 GPUs it's ~7.9 hours, and at 131,072 GPUs it drops to just 14 minutes.
3. When debugging an NCCL timeout, which rank is most likely the root cause?
NCCL timeouts are reported by ranks waiting for a response. The actual culprit is typically the rank that went silent — it crashed, hung, or lost connectivity before participating in the collective.
4. What parallelism strategy is best suited for intra-node communication (high NVLink bandwidth)?
Tensor Parallelism splits individual layers across GPUs and requires high-bandwidth, low-latency communication for every forward/backward pass. NVLink (900 GB/s) within a node makes this feasible.
5. What is FSDP/ZeRO-3's primary benefit?
ZeRO-3 (FSDP) shards parameters, gradients, AND optimizer states across all GPUs. Each GPU stores only 1/N of the full model state, enabling N-times-larger models. Trade-off: increased communication to gather parameters on-demand.
6. Reflection AI was founded by researchers from which organization?
Both founders came from Google DeepMind. Ioannis was employee #25 who built AlphaGo/AlphaZero/MuZero. Misha led reward modeling for Gemini. They left in early 2024 to start Reflection.
7. In an "Agentic Coding" interview, what is the MOST important signal when using AI tools?
The interview assesses judgment — knowing when to use AI (boilerplate, syntax, tests) vs. when to think independently (architecture, trade-offs). Critically reviewing AI output is the key differentiator.
8. What XID error code indicates "GPU has fallen off the bus"?
XID 79 = PCIe link failure (GPU inaccessible). XID 48 = double-bit ECC (uncorrectable memory). XID 63 = row remapping failure. All are critical hardware failures requiring node replacement.
9. What is Reflection's core technical thesis?
Reflection's thesis: frontier intelligence requires combining large-scale LLM pretraining with advanced RL — the same techniques that powered AlphaGo, now applied to language models. Distinct from just scaling or just post-training RLHF.
10. When a training job resumes from checkpoint and loss immediately spikes, what should you check FIRST?
An immediate, large loss spike most commonly indicates model parameters loaded onto incorrect ranks — e.g., pipeline stage 3's weights on stage 1's GPU. LR issues cause gradual degradation, not instant spikes.

Design Survey

Design a system to train a 1-trillion parameter MoE model. +

Hybrid parallelism. Within each node (8 GPUs, NVLink): tensor parallelism for dense layers. Across nodes: pipeline parallelism for sequential stages. MoE layers: expert parallelism — each expert on a dedicated GPU with routing network dispatching tokens. Data parallelism across the outer dimension. Critical challenges: load balancing across experts, communication overhead for token routing, memory for optimizer states. ZeRO-3 for optimizer sharding, auxiliary loss for balanced expert utilization.

What's the difference between RDMA and TCP/IP, and why does it matter? +

TCP/IP goes through the kernel stack — data copies from user space to kernel buffers, through protocol stack, out the NIC. Each hop adds latency and CPU overhead. RDMA bypasses all of that — NIC reads directly from application memory, writes directly to remote memory. Zero CPU, zero copies, ~1-2μs vs ~50-100μs for TCP. For distributed training, this matters because AllReduce happens every step — shaving microseconds per collective saves hours over multi-day runs across thousands of GPUs.

How would you handle heterogeneous GPU generations in a cluster? +

Never mix generations within a single job's data-parallel group — faster GPUs idle waiting for slower ones. Instead, use different generations for different workloads: frontier GPUs for main training, older for evaluation, preprocessing, or smaller experiments. If you must mix, consider local SGD where faster workers take more steps between sync — but this introduces optimization challenges. Cleanest: homogeneous allocation per job, heterogeneous scheduling across jobs.

Case Study

40% throughput degradation, no errors. Walk me through debugging. +

No errors but degraded throughput = straggler problem. Step 1: Per-GPU utilization across all nodes — look for outliers. Step 2: For slow GPUs, check thermal state (throttling?), clock speeds (power-capped?), memory bandwidth (ECC corrections?). Step 3: Network — are collective latencies uniform or is one node consistently late? NCCL debug logging for per-rank timing. Step 4: Data pipeline — is one worker's dataloader slower (disk I/O, slow NFS)? The 40% without errors strongly suggests thermal throttling or network degradation creating straggler effects on synchronous collectives.

What signals should automatically detect a degrading GPU? +

Five key signals: (1) ECC error rate — single-bit corrections trending up predict double-bit failures. Alert at 10+/hour. (2) Temperature trend — sustained >78°C predicts throttling. (3) NVLink CRC error rate — any non-zero = link degradation. (4) PCIe replay count — increasing = marginal link. (5) Clock speed vs expected under load. Correlate signals: elevated ECC AND temperature → quarantine immediately. Proactive replacement during maintenance is always cheaper than mid-training crash.

Design automated remediation for node failures during training. +

Three phases: Detect, Isolate, Recover. Detection: continuous health monitoring plus job-level watchdogs (rank no progress in N seconds = failure). Isolation: mark node unhealthy, prevent new allocations, notify checkpoint coordinator. Recovery: auto checkpoint on healthy ranks, allocate replacement from spare pool, health-validate replacement, restart from checkpoint. Target MTTR: under 5 minutes. Spare pool sized on historical failure rates — typically 2-5% of cluster capacity. Trade-off: more spares = faster recovery but higher cost.

Culture

What does "do the simple thing that works" mean to you? +

Resisting the urge to over-engineer on first pass. Ask: what's the simplest architecture that solves today's problem correctly? Not the one handling hypothetical future requirements or using the most sophisticated algorithm — the one that works, is understandable, and changeable. In practice: database before custom storage, cron before event-driven architecture, monolith before microservices. Add complexity when you have evidence it's needed. You can rarely remove it once it's there.

How do you stay current with the rapidly evolving AI/ML landscape? +

A few high-signal sources rather than everything: key arxiv papers (tracking trusted authors), select technical blogs, and reproducing interesting results in small-scale experiments. But the best way is building things. When a new technique appears — a new RL algorithm or training optimization — I implement a simplified version to understand it mechanically. Papers give the "what," implementing gives the "why" and "where does this break."
