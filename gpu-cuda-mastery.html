The warp size of 32 is fundamental to CUDA programming. It determines coalesced memory access patterns, warp-level primitives like __shfl_sync(), and the minimum divergence granularity. Getting this wrong signals unfamiliarity with the execution model.

This is why we align memory accesses to 32-element boundaries and why branch divergence within a warp serializes both paths. AMD uses 64-thread wavefronts on CDNA, which is probably where the confusion comes from.

Section 03 — Deep Dive

Hopper Architecture: The Full Picture

Understanding how an SM is organized — and what lives inside it — is the mental model that prevents all three myths above from recurring.

Inside One Hopper SM

Each of the 132 SMs in H100 SXM contains:

128 FP32 CUDA cores (organized as 4 processing blocks of 32)
64 FP64 cores (half the FP32 count)
64 INT32 cores
4 Tensor Cores (4th gen, supporting FP8/FP16/BF16/TF32/FP64)
4 Texture units
256 KB combined L1/shared memory (configurable split)
1 Tensor Memory Accelerator (TMA) — new in Hopper

The Execution Model

Threads are grouped into warps of 32. Each SM can hold up to 64 active warps (2,048 threads). The warp scheduler picks ready warps each cycle — this latency hiding is how GPUs achieve high throughput despite individual thread stalls.

A thread block (max 1,024 threads) maps to one SM and shares that SM's shared memory. Multiple blocks can co-reside on one SM if resources allow — this is occupancy.

Shared Memory Best Practices

Bank conflicts: Shared memory is divided into 32 banks (one per warp lane). Accessing the same bank from multiple threads in a warp serializes — design your access patterns to hit different banks.

Async copy: Hopper's TMA can load directly from global to shared memory without going through registers, freeing up compute threads. Use cp.async or the TMA descriptor API.

The Roofline Mental Model

A kernel is either compute-bound (limited by FLOPS) or memory-bound (limited by bandwidth). The crossover point is the arithmetic intensity = FLOPs / Bytes loaded.

For H100 SXM: the ridge point is ~67 TFLOPS / 3.35 TB/s ≈ 20 FLOPs/byte. Kernels below this ratio are memory-bound — which is most LLM inference.

The tile size is chosen to avoid bank conflicts across the 32 shared memory banks."

NVLink & Interconnect: The Multi-GPU Story

You mentioned NVLink correctly in context but couldn't provide bandwidth numbers. Here's the full picture — from a single link to a full DGX node.

NVLink 4.0 (Hopper)

Per link: 50 GB/s bidirectional (25 GB/s each direction)
Links per GPU: 18 (H100 SXM5)
Total per GPU: 18 × 50 = 900 GB/s bidirectional
Comparison: PCIe Gen5 x16 = ~128 GB/s bidirectional

NVLink 4.0 is 7× faster than PCIe Gen5 for GPU-to-GPU communication.

NVSwitch (3rd gen)

In a DGX H100 (8 GPUs), four NVSwitch chips create a fully-connected topology — every GPU can talk to every other GPU at the full 900 GB/s without routing through intermediaries.

Total bisection bandwidth: 3.6 TB/s across the node. This enables all-reduce operations for distributed training to complete in microseconds rather than milliseconds.

Why This Matters for Training

In data-parallel training, gradients must be synchronized across GPUs every iteration. With 8 GPUs doing all-reduce over NVLink at 900 GB/s each, a 1 GB gradient tensor synchronizes in roughly 1.1 ms. Over PCIe Gen5 at 128 GB/s, the same operation takes ~7.8 ms — a 7× slowdown that directly reduces training throughput.

NVLink 4.0 on H100 provides 900 gigabytes per second of bidirectional bandwidth per GPU through 18 links at 50 GB/s each. That's seven times PCIe Gen5, which is why multi-GPU training scales almost linearly within a node — the communication overhead for all-reduce is under 2 milliseconds even for large gradient tensors.

Q6: What is the shared memory bank count in NVIDIA GPUs?
✅ Shared memory has 32 banks (matching the warp size of 32). Successive 4-byte words map to successive banks. Bank conflicts occur when multiple threads in a warp access different addresses in the same bank.

Mock Interview: Model Answers

Read each answer aloud. Fluency comes from the mouth, not the eyes. Practice until these feel natural — then riff on them in your own style.

Walk me through the H100 architecture at a high level. +

The H100 is built on the Hopper architecture using TSMC's 4N process with 80 billion transistors. The SXM5 variant has 132 Streaming Multiprocessors, each containing 128 FP32 CUDA cores and 4 fourth-generation Tensor Cores — that's 16,896 CUDA cores and 528 Tensor Cores total. It pairs with 80 GB of HBM3 at 3.35 TB/s bandwidth and connects to other GPUs via 18 NVLink 4.0 links at 900 GB/s aggregate. The key Hopper innovations are FP8 Tensor Cores for doubled AI throughput, the Tensor Memory Accelerator for async data movement, and the DPX instructions for dynamic programming workloads.

What's the difference between a CUDA core and a Tensor Core? +

A CUDA core is a scalar FP32 processing unit — it does one fused multiply-add per clock per thread. A Tensor Core is a dedicated matrix engine that performs a full 16-by-8-by-16 matrix multiply-accumulate in a single clock cycle across multiple precisions including FP8, FP16, BF16, and TF32. They're physically separate hardware on the die with different instruction sets — you invoke Tensor Cores through wgmma or mma.sync PTX instructions, or implicitly through cuBLAS and cuDNN. The H100 has 16,896 CUDA cores but only 528 Tensor Cores, yet those 528 Tensor Cores deliver 30 times more FLOPS for matrix workloads.

Explain the CUDA memory hierarchy and how you'd optimize a kernel for it. +

The hierarchy goes registers, shared memory, L1 cache, L2 cache, then HBM global memory — each level trading capacity for latency. Registers are free but limited to 255 per thread. Shared memory gives you 228 KB per SM at roughly 20-cycle latency with 19 TB/s bandwidth, but you need to manage bank conflicts across its 32 banks. L2 is 50 MB shared across all SMs. HBM3 gives you 80 GB at 3.35 TB/s but 400-plus cycle latency. My optimization approach is: first, tile data into shared memory to exploit reuse; second, ensure coalesced global memory accesses aligned to 128-byte cache lines; third, use async copy or TMA to overlap data movement with compute; and fourth, tune occupancy so the warp scheduler always has ready warps to hide that HBM latency.

How does NVLink compare to PCIe for multi-GPU training? +

NVLink 4.0 on H100 provides 900 GB/s bidirectional bandwidth per GPU — that's seven times PCIe Gen5's 128 GB/s. In a DGX H100, four NVSwitch chips create a full-mesh topology so all eight GPUs communicate at that full rate simultaneously, giving 3.6 TB/s bisection bandwidth. For data-parallel training, this means all-reduce on a 1 GB gradient tensor takes about 1 millisecond over NVLink versus 8 milliseconds over PCIe. That difference compounds every iteration, so NVLink-connected systems achieve near-linear scaling for distributed training within a node.

What is a warp and why does warp size matter for performance? +

A warp is 32 threads that execute in SIMT lockstep — same instruction, same cycle. Warp size matters because it's the granularity of everything: memory coalescing happens at warp level, so you want 32 consecutive threads accessing consecutive addresses for a single 128-byte transaction. Branch divergence serializes at warp level — if threads in a warp take different paths, both paths execute sequentially. And warp-level primitives like shuffle let threads exchange data without going through shared memory, which is critical for reductions. The 32-thread warp has been constant since NVIDIA's first CUDA GPU, so it's a safe architectural assumption for any CUDA code.
